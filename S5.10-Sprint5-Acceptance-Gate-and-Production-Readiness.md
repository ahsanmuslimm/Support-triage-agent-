# S5.10 — Sprint 5 Acceptance Gate & Production Readiness

**Sprint:** 5 (Proactive Intelligence & Optimization)  
**Deliverable:** End-to-end acceptance scenarios, production readiness checklist, load test, golden test set  
**Effort:** 1 day  
**Dependencies:** S5.1–S5.9 (all Sprint 5 components)

---

## Overview

**Acceptance gate** validates all Sprint 5 features before production promotion. This deliverable ensures:
- Lifecycle detection (S5.1) correctly stages customers across Growth → Active → Mature → At-Risk → Churning
- Churn prediction (S5.2) identifies churn signals 72h in advance with > 85% precision
- Recommendation acceptance (S5.3) weights articles by successful resolutions
- Campaign ROI measurement (S5.4) quantifies lift and cohort impact
- Performance benchmarks met under load

The acceptance gate defines a **production readiness checklist**, **performance SLAs**, **load test procedure**, and **30-record golden test set** that validates end-to-end workflows across all Sprint 5 services.

## Technical Specification

### 1. Performance Benchmarks

All benchmarks measured end-to-end; include network latency.

```
Lifecycle Detection:
  - Single customer stage update: < 500ms (p95)
  - Batch of 1000 customers: < 2s (p95)
  - Monthly recalculation run: < 5 minutes

Churn Prediction:
  - Single customer prediction: < 1s (p95)
  - Batch of 1000 customers: < 30s (p95)
  - Model inference (excluding data fetch): < 200ms (p99)

Recommendations:
  - Query KB index for 1 customer: < 500ms (p95)
  - Rank & re-weight 10 recommendations: < 300ms (p95)
  - Batch recommend for 100 customers: < 15s (p95)

Campaign ROI:
  - Single campaign measurement: < 2s (p95)
  - Cohort comparison (2 groups × 1000 customers): < 5s (p95)
  - Report generation (HTML + JSON): < 1s (p95)

System-wide Load:
  - 1000 req/s sustained for 5 minutes across all Sprint 5 APIs
  - P99 latency: < 2s for any endpoint
  - Error rate: < 0.1% (< 5 errors per 500k requests)
  - Memory stability: no growth > 10% over 5min window
```

## Acceptance Scenarios

### Scenario 1: Customer Lifecycle Transition (Growth → Churning)

**Objective:** Verify automatic lifecycle stage detection and retention strategy activation.

**Setup:**
```json
{
  "customer_id": 20001,
  "initial_state": {
    "account_age_days": 180,
    "total_orders": 12,
    "total_spent": 2400,
    "last_order_days_ago": 45,
    "subscription_status": "active",
    "support_interaction_count_90d": 2,
    "nps_score": 6,
    "support_satisfaction": 0.65
  }
}
```

**Execution Steps:**

1. **Initial Stage Assessment**
   - Call `POST /lifecycle/update_stage` with customer_id=20001
   - Assert: `stage == "Mature"` (180 days, 12 orders, active)
   - Assert: `stage_confidence >= 0.85`

2. **Trigger Churn Signals**
   - Simulate no orders for 60 days (update last_order_days_ago → 60)
   - Simulate 3 failed support tickets (satisfaction drop to 0.30)
   - Simulate NPS drop to 2 (detractor)
   - Post update event to `POST /lifecycle/update_stage`

3. **Verify Stage Transition**
   - Assert: `stage == "Churning"` (within 1 processing cycle, < 5s)
   - Assert: `previous_stage == "Mature"`
   - Assert: `stage_transition_reason` contains "no_recent_orders" + "low_satisfaction"
   - Assert: `stage_updated_at` is recent (< 5s ago)

4. **Verify Retention Strategy Activation**
   - Query `GET /retention-strategy?customer_id=20001`
   - Assert: Response contains retention tactics:
     ```json
     {
       "strategy_id": "s_4021",
       "tactics": [
         {"type": "winback_email", "offer": "20% discount", "priority": 1},
         {"type": "churn_survey", "priority": 2},
         {"type": "vip_call", "assigned_to": "support_manager", "priority": 3}
       ],
       "activated_at": "2024-01-20T14:32:10Z"
     }
     ```
   - Assert: Retention campaign triggered within 5 minutes

5. **Verify Monitoring & Alerts**
   - Assert: Lifecycle stage change logged to audit trail
   - Assert: Alert rule triggered for "Mature → Churning" transition
   - Assert: On-call team notified via Slack

**Expected Outcome:** Customer stage transitions from Mature → Churning within one processing cycle; retention strategy activates automatically.

**Objective:** Verify early churn signal detection and campaign offer generation 72h before likely churn.

**Execution Steps:**

1. **Trigger Churn Signal Pattern**
   - Simulate declining feature usage: feature_usage_30d drops 12 → 4 → 1 over 3 updates
   - Simulate support friction: failed ticket resolution, abandonment in chat
   - Simulate engagement drop: no login for 5 days

   - Assert: `churn_prediction.predicted_churn_window == "72h"` (within 72 hours)
   - Assert: `churn_prediction.confidence >= 0.80`
   - Assert: `churn_prediction.top_reasons` includes:
     ```json
     [
       {"factor": "declining_engagement", "contribution": 0.35},
     ```

3. **Verify Campaign Offer Generated**

4. **Verify Message Delivery**

5. **Verify Tracking & Attribution**

   - Assert: Tracking pixel placed in email; UTM params set
   - Assert: Analytics event logged: `event_type = "churn_winback_campaign_sent"`
   - Assert: Campaign outcome tracked for 14-day window

**Expected Outcome:** Churn prediction fires with 72h horizon; retention campaign offer automatically generated and delivered across email + SMS + in-app; campaign tracked for ROI measurement.

### Scenario 3: Recommendation Acceptance & Weight Update

**Objective:** Verify KB article recommendations accepted, resolution logged, and recommendation weight algorithm updated.

**Setup:**
```json
{
  "customer_id": 20003,
  "support_ticket_id": "tkt_8401",
  "issue_category": "billing",
  "description": "Customer asking about invoice discrepancies",
  "initial_recommendation_weights": {
    "article_401": 0.15,
    "article_402": 0.12,
    "article_403": 0.08
  }
}
```

**Execution Steps:**

1. **Generate Recommendations**
   - Call `POST /recommendations/query` with:
     ```json
     {
       "customer_id": 20003,
       "support_ticket_id": "tkt_8401",
       "issue_category": "billing",
       "context": "Invoice discrepancy query"
     }
     ```
   - Assert: Response includes top 5 ranked KB articles:
     ```json
     {
       "recommendations": [
         {"article_id": 401, "score": 0.92, "rank": 1, "title": "Understanding Invoice Line Items"},
         {"article_id": 402, "score": 0.87, "rank": 2, "title": "Common Billing Issues & Fixes"},
         {"article_id": 403, "score": 0.79, "rank": 3, "title": "Refund & Credit Process"}
       ]
     }
     ```

2. **Simulate Article Click & View**
   - Customer clicks article_401 in support interface
   - Article page loads; customer views for 3+ minutes
   - Assert: Click event logged:
     ```json
     {
       "event_type": "kb_article_click",
       "article_id": 401,
       "customer_id": 20003,
       "ticket_id": "tkt_8401",
       "timestamp": "2024-01-20T11:22:00Z"
     }
     ```

3. **Log Resolution Success**
   - Agent marks ticket resolved after article provided
   - Support staff selects: "Resolution: KB article helped"
   - Call `POST /resolution/log` with:
     ```json
     {
       "ticket_id": "tkt_8401",
       "article_id": 401,
       "resolution_type": "kb_article_resolved",
       "customer_satisfaction": "resolved",
       "resolution_time_minutes": 8
     }
     ```
   - Assert: Resolution logged with article attribution

4. **Verify Weight Update in Offline Process**
   - Trigger recommendation weight update job (or wait for scheduled run)
   - Query weight history: `GET /recommendations/weights/article/401?start=now-1d`
   - Assert: New weight calculation reflects:
     ```json
     {
       "article_id": 401,
       "previous_weight": 0.15,
       "new_weight": 0.18,
       "update_reason": "resolution_success",
       "successful_resolutions_30d": 28,
       "total_shows_30d": 145,
       "success_rate": 0.193,
       "algorithm_version": "v2.3"
     }
     ```
   - Assert: New weight > previous weight (positive reinforcement)

5. **Verify Future Recommendations Reflect Update**
   - Wait 1 minute (cache invalidation window)
   - Call `POST /recommendations/query` for different customer with similar issue
   - Assert: article_401 appears higher in ranking due to updated weight

6. **Verify Metrics & Analytics**
   - Query analytics: `GET /analytics/recommendations?metric=resolution_rate&article_id=401&period=30d`
   - Assert: Resolution rate metric updated
   - Assert: Dashboard reflects improved performance for article_401

**Expected Outcome:** KB recommendation clicked, resolution logged, recommendation weight algorithm updated via offline batch process, future recommendations reflect improved scoring.

**Execution Steps:**

1. **Verify Cohorts Assigned**
   - Query `GET /campaigns/camp_5020/cohorts`

   - Assert: Cohorts non-overlapping

**Golden Test Set Validation Script:**

```python
async def validate_golden_test_set():
    """Execute all 30 golden tests end-to-end."""
    
    with open("golden_test_set.jsonl") as f:
        golden_tests = [json.loads(line) for line in f]
    
    results = []
    
    for test in golden_tests:
        try:
            # 1. Lifecycle detection
            lifecycle_resp = await lifecycle_service.update_stage(
                customer_id=test["customer_id"],
                initial_state=test["initial_state"]
            )
            
            stage_match = lifecycle_resp["stage"] == test["expected_outputs"]["lifecycle_stage"]
            assert stage_match, f"Stage mismatch: {lifecycle_resp['stage']}"
            
            # 2. Churn prediction
            churn_resp = await churn_service.predict(
                customer_id=test["customer_id"]
            )
            
            churn_score = churn_resp["score"]
            expected_range = test["expected_outputs"]["churn_score_range"]
            assert expected_range[0] <= churn_score <= expected_range[1], \
                f"Churn score {churn_score} outside range {expected_range}"
            
            # 3. Recommendations
            rec_resp = await recommendations_service.query(
                customer_id=test["customer_id"]
            )
            
            rec_ids = [r["article_id"] for r in rec_resp["recommendations"]]
            expected_ids = set(test["expected_outputs"]["recommendation_article_ids"])
            matched = len(set(rec_ids) & expected_ids)
            min_match = test["expected_outputs"]["recommendation_article_ids_min_match"]
            assert matched >= min_match, \
                f"Recommendation match {matched} < {min_match}"
            
            # 4. Campaign ROI (if applicable)
            if "campaign_id" in test:
                roi_resp = await roi_service.measure(
                    campaign_id=test["campaign_id"]
                )
                assert roi_resp["roi"] > 0, "Negative ROI"
            
            results.append({
                "test_id": test["test_id"],
                "status": "PASS",
                "lifecycle_stage": lifecycle_resp["stage"],
                "churn_score": churn_score,
                "recommendations_count": len(rec_ids)
            })
        
        except AssertionError as e:
            results.append({
                "test_id": test["test_id"],
                "status": "FAIL",
                "error": str(e)
            })
    
    return results
```

## Deployment Procedure

### Phase 1: Blue/Green Environment Preparation (T-2 hours)

1. **Clone Blue to Green**
   - Spin up green environment with identical resources to blue
   - Copy all configuration from blue (DB, Redis, secrets)
   - Deploy Sprint 5 services to green with latest code

2. **Validate Green Environment**
   - Health checks passing for all 5 services
   - Database migrations applied successfully
   - Feature flags set to 0% (dark launch, no traffic)
   - Smoke tests passing in green
   - Golden test set validation passing in green

3. **Pre-deployment Communication**
   - Notify support team: deployment starting at T+0
   - Brief on-call team on rollback procedure
   - Set expectation: gradual traffic ramp, 4 hours total

### Phase 2: Traffic Ramp (T+0 to T+4 hours)

**T+0 (10% traffic): Baseline validation**
- Route 10% of requests to green
- Monitor for 30 minutes:
  - [ ] Error rate stable (< 0.1%)
  - [ ] P99 latency < 2s
  - [ ] No increase in exception logs
  - [ ] Model inference latency nominal
- Alerts active on all metrics
- On-call standing by

**T+0:30 (25% traffic): Expanded validation**
- Increase to 25% traffic (if 10% cohort successful)
- Monitor for 1 hour:
  - [ ] Error rate remains < 0.1%
  - [ ] Latency percentiles stable
  - [ ] No cascade failures
  - [ ] Revenue impact (if applicable) neutral
- Continue heightened alerting

**T+1:30 (50% traffic): Half-canary**
- Increase to 50% traffic (if 25% cohort successful)
- Monitor for 1.5 hours:
  - [ ] All SLI metrics green
  - [ ] No customer-facing issues reported
  - [ ] Database replication lag < 5s
  - [ ] Feature flag toggle works (kill switch test)
- On-call ready to roll back

**T+3:00 (100% traffic): Full promotion**
- Route 100% of traffic to green
- Monitor for 1 hour:
  - [ ] All metrics nominal
  - [ ] No degradation vs blue baseline
  - [ ] Customer impact: zero
- Declare deployment successful

### Phase 3: Post-Deployment (T+4 hours onward)

**T+4 to T+76 hours: 72-hour heightened monitoring**

- Alert thresholds tightened:
  - Error rate > 0.05% (vs normal 0.1%)
  - P99 latency > 1.5s (vs normal 2s)
- On-call on standby (reduced to warning escalation, not immediate page)
- Daily metric review meetings scheduled
- Feature flags can be adjusted (kill switch always available)

**Post-72h: Declare blue environment for decommission or standby**

### Rollback Triggers

Automatic rollback triggered if ANY of:

| Condition | Threshold | Action |
|-----------|-----------|--------|
| Error rate spike | > 0.5% (vs < 0.1% baseline) | Immediate rollback |
| P99 latency spike | > 3x baseline (> 6s) | Immediate rollback |
| Service health check | 1+ service down | Immediate rollback |
| Revenue impact | > 5% drop vs blue cohort | Immediate rollback |
| Data corruption | Any data inconsistency detected | Immediate rollback |

**Rollback Procedure (5-minute recovery):**

1. DNS flip: 100% traffic → blue environment (immediate)
2. Feature flags: disable Sprint 5 features (parallel to DNS flip)
3. Verify: blue environment healthy, error rate recovered
4. Post-mortem: identify failure cause within 24h
5. Fix + re-test: before attempting green deployment again
