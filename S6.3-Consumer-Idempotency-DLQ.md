## Overview

### What This Delivers

S6.3 adds resilience guarantees to the event system:

**Problem**: Kafka can deliver the same event multiple times (retries, crashes)
**Solution**: Idempotency store + Dead Letter Queue

**Key Artifacts**:
- `services/api/src/triage/adapters/idempotency.py` - Dual-write idempotency (Redis + Postgres)
- `services/api/src/triage/adapters/dlq.py` - Dead letter queue with replay
- `services/api/src/triage/adapters/event_consumer.py` - Resilient consumer with retries
- `packages/py_core/alembic/versions/0008_sprint6_idempotency_dlq.py` - Database migrations
- `services/api/tests/test_adapters_kafka.py` - Comprehensive test suite

### Design Principles

1. **Dual-Write Strategy**: 
   - Fast path (Redis): For high-volume events (7-day TTL)
   - Slow path (Postgres): For critical events (durable)

2. **Atomic Insert-First** (M2 Fix):
   - Use `INSERT ... ON CONFLICT DO UPDATE` (atomic, no race conditions)
   - Record that event was processed
   - On duplicate: return cached result

3. **Retry Policy**: 
   - Exponential backoff (1s, 10s, 60s)
   - Max 3 retries before DLQ
   - Manual replay from DLQ

4. **Partition Key Reuse** (S6.3 H5 Fix):
   - Kafka publishes event with UUID
   - Consumer receives same UUID (idempotency key)
   - Maps to database idempotency record

## Architecture

### Idempotency Store

```
Event arrives (event_id = "evt_123", tenant_id = "tenant_1")
    ↓
Check idempotency store:
  - Redis: Key = "idempotency:tenant_1:evt_123" (fast path)
  - If found: Return cached result → Event processed ✓
  - If not found: Continue to processing
    ↓
Process event (apply business logic)
    ↓
Record in idempotency store:
  - Redis: Store result with 7-day TTL (fast path)
  - Postgres: Insert with ON CONFLICT (slow path, if critical)
    ↓
Return result ✓
```

### Fast Path (Redis)

```python
# Check: O(1) lookup
existing = await redis.get("idempotency:tenant_1:evt_123")
if existing:
    return cached_result  # Duplicate

# Record: O(1) insert with TTL
await redis.setex(
    "idempotency:tenant_1:evt_123",
    604800,  # 7 days in seconds
    "processed_ok",
)
```

**Trade-off**: Fast but loses state on Redis restart (acceptable for non-critical events)

### Slow Path (Postgres)

```python
# Atomic insert-or-fetch (M2 Fix)
INSERT INTO triage.idempotency_records 
  (tenant_id, event_id, event_type, result_json, processed_at, is_first_attempt)
VALUES 
  ('tenant_1', 'evt_123', 'message.ingested', '{}', NOW(), true)
ON CONFLICT (tenant_id, event_id)
DO UPDATE SET
  result_json = idempotency_records.result_json,  -- Keep original
  is_first_attempt = false
RETURNING is_first_attempt;

-- Result: is_first_attempt = true (new) or false (duplicate)
```

**Why ON CONFLICT?**
- Atomic: PostgreSQL handles conflict internally
- No race conditions: Avoids duplicate key exception handling
- Deterministic: Always succeeds (no retry logic needed)

**Trade-off**: Durable but slower (~10ms insert)

## Dead Letter Queue (DLQ)

### Schema

```sql
CREATE TABLE triage.dlq_events (
    id UUID PRIMARY KEY,
    tenant_id UUID,
    original_event_id VARCHAR(255),
    original_event TEXT,  -- JSON
    error TEXT,
    error_type VARCHAR(100),
    retry_count INTEGER,
    replayed_at TIMESTAMP,
    created_at TIMESTAMP,
);

CREATE INDEX idx_dlq_created_at ON dlq_events(created_at);
CREATE INDEX idx_dlq_replayed ON dlq_events(replayed_at) WHERE replayed_at IS NULL;
```

### Workflow

```
Event processing fails after 3 retries
    ↓
Send to DLQ (Kafka topic: triage.dlq + Postgres table)
    ↓
Operator investigates error
    ↓
Fix root cause (external service restored, etc.)
    ↓
Manually replay event via CLI:
  $ triage-cli dlq replay evt_123
    ↓
Event reprocessed with same idempotency key
    ↓
Success or fail again → stays in DLQ for investigation
```

## Implementation

### IdempotencyStore (idempotency.py)

```python
class IdempotencyStore:
    async def check_or_record(
        self,
        tenant_id: str,
        event_id: str,
        event_type: str,
        use_slow_path: bool = False,
    ) -> IdempotencyResult:
        """Check if event was already processed; record if not."""
        
        if use_slow_path and self.db_session:
            return await self._check_or_record_slow_path(...)
        else:
            return await self._check_or_record_fast_path(...)
```

**Selection Logic**:
- **Default**: Fast path (Redis) for high volume (message.ingested, action.executed)
- **Critical**: Slow path (Postgres) for sensitive operations (refunds, chargebacks)

### ResilientEventConsumer (event_consumer.py)

```python
class ResilientEventConsumer:
    async def consume_with_retry(
        self,
        event: Dict[str, Any],
        handler_func: Callable,
        use_slow_path: bool = False,
    ) -> None:
        """Consume event with retry policy."""
        
        for attempt in range(self.max_retries + 1):
            try:
                # Check idempotency
                result = await self.idempotency.check_or_record(...)
                if result.is_duplicate:
                    return  # Already processed
                
                # Execute handler
                await handler_func(event)
                return
                
            except Exception as e:
                if attempt < self.max_retries:
                    # Retry with backoff
                    await asyncio.sleep(self._get_backoff(attempt))
                else:
                    # Max retries exceeded
                    await self.dlq.send_to_dlq(event, e, retry_count=attempt)
```

**Retry Backoff**:
- Attempt 0: 0ms
- Attempt 1: 1s delay
- Attempt 2: 10s delay
- Attempt 3: 60s delay
- Attempt 4+: Send to DLQ

## FAQ

**Q: Can we replay events from DLQ?**  
A: Yes. Replay with same event_id triggers idempotency check. If processing now succeeds, event marked as processed. Safe idempotent operation.

**Q: What if idempotency store fails?**  
A: Fast path (Redis): May process duplicate, idempotent handler should handle. Slow path (Postgres): Atomic operation guarantees no duplicates.

**Q: How long do we keep DLQ events?**  
A: Indefinitely (for audit). Query by replayed_at to find resolved events.

**Q: What's the latency impact?**  
A: Fast path: <1ms. Slow path: ~10ms. Compression via batching and caching.
