### 1. `tests/acceptance/features/scenarios.feature` (Gherkin Features)
```gherkin
# language: en
Feature: Triage Agent MVP - Acceptance Scenarios
  As a support team
  I want an AI triage agent that resolves Tier-1 issues autonomously
  So that customers get instant answers and human agents focus on complex cases

  @pending
  Scenario: J1 - Autonomous WISMO Resolution (Order Status)
    Given a design-partner tenant \"ecommerce-tenant\"
    And a web chat channel for the tenant
    And Shopify integration with sample orders
    And the intent \"order.status\" has autonomy level L3 (autonomous)
    
    When a customer writes \"Where's my order #ORD-20240115-5678?\"
    And the message is ingested via web chat
    
    Then the message is classified as intent \"order.status\" with confidence ≥ 0.95
    And the order ID \"ORD-20240115-5678\" is extracted and verified against Shopify
    And the shipping status is retrieved: \"Delayed, new ETA tomorrow\"
    And an AI-composed answer is generated with citation to tracking link
    And the answer is grounded (groundedness ≥ 0.95)
    And no output guard blocks the answer
    And the answer is sent to the customer in < 4 seconds
    And the conversation is auto-resolved with outcome \"success\"
    And a CSAT survey is triggered

  @pending
  Scenario: J2 - Multi-Intent with Partial Autonomy & Handoff
    Given a design-partner tenant \"ecommerce-tenant\"
    And Stripe integration with subscription data
    And the intent \"refund.request\" has autonomy level L0 (draft only)
    And the intent \"shipping.status\" has autonomy level L3 (autonomous)
    And a refund approval workflow at $150+ threshold
    
    When a customer writes in anger: \"I want a refund for the blue jacket AND my other order still hasn't shipped. This is ridiculous.\"
    
    Then the message is classified with intents [\"refund.request\", \"shipping.status\"]
    And sentiment is detected as \"negative\" with frustration flag
    And urgency score is 78 (P2 priority)
    And the jacket order ($240) is extracted and verified
    And the system resolves the shipping status autonomously
    And the refund is flagged for approval (exceeds $150 auto-limit)
    And an approval request is posted to Slack
    And a draft answer is generated for the customer
    And the draft waits for supervisor approval
    When the supervisor approves in Slack
    Then the Temporal workflow executes the Stripe refund
    And the customer is notified of approval with refund ETA
    And both issues are marked resolved

  @pending
  Scenario: J3 - Critical Escalation with Full Context
    Given a design-partner tenant \"saas-tenant\"
    And the intent \"auth.sso_failure\" is marked human_only (autonomy L0)
    
    When an admin writes: \"Our SSO stopped working after your update, 200 users locked out\"
    And 12 similar tickets arrive within 30 minutes (incident cluster)
    
    Then the message is classified as \"auth.sso_failure\"
    And the incident cluster is detected (12 similar tickets)
    And urgency score is 95 (P1 – critical incident)
    And the hard-escalation trigger \"data breach / safety\" is not present (false alarm)
    But the pattern triggers immediate escalation
    And a handoff packet is generated with:
      - Summary of the issue
      - Customer account (Enterprise, $180K ARR)
      - Renewal date (41 days out)
      - Incident cluster link
      - Suggested runbook
    And the handoff is posted to the Zendesk sidebar for the agent
    And an on-call Slack alert is sent to the Identity team
    And no attempt is made for autonomous resolution

  @pending
  Scenario: J4 - Proactive Outreach (Failed Payment Recovery)
    Given a design-partner tenant \"saas-tenant\"
    And a Stripe integration receiving webhooks
    And the \"dunning-assist\" proactive trigger configured
    
    When a Stripe event arrives: invoice.payment_failed for customer \"cust-123\"
    
    Then suppression checks pass:
      - No outreach in last 7 days
      - Not in quiet hours (customer timezone)
      - Account not in collections
    And an in-app message is composed offering to update payment
    And an email is sent with a secure payment update link
    And a Temporal workflow schedules a follow-up message in 24 hours if not completed
    And conversion is tracked (payment updated / retry succeeded)

  @pending
  Scenario: J5 - Admin Safely Tunes Autonomy (Shadow → Assist → Autonomous)
    Given a design-partner tenant \"ecommerce-tenant\"
    And the intent \"returns.policy_question\" running in shadow mode
    And 1,200 historical decisions logged
    
    When the admin reviews intent metrics:
      - Classification accuracy: 96%
      - Groundedness: 0.97
      - False positive rate: 0.2%
    And the admin promotes from L1 (Assist) to L3 (Autonomous) on web_chat channel only
    
    Then the configuration change is versioned (v1.2.3)
    And the change is logged to the audit trail with hash chain
    And the promotion takes effect within 10 seconds
    And metrics are tracked separately (v1.2.2 vs v1.2.3) for A/B comparison
    And the admin can roll back with one click if issues emerge

  @pending
  Scenario: J6 - Agent Feedback Feeds Weekly Learning Loop
    Given a design-partner tenant \"ecommerce-tenant\"
    And a message originally classified as \"billing.invoice_question\"
    
    When an agent re-tags the conversation as \"billing.tax_exemption\"
    And the agent saves the correction
    
    Then the feedback signal is captured in feedback_signals table
    And the signal includes:
      - Original prediction
      - Agent correction
      - Confidence of original
      - Timestamp
    And the signal is marked for the weekly training pipeline
    When the weekly retraining pipeline runs (Tuesday 2 AM)
    Then a new classifier model is trained with the correction
    And the model is evaluated against the golden set
    And if evaluation passes (top-1 ≥ 90%, macro-F1 ≥ 85%):
      - Model is shadowed for 24 hours
      - Metric comparison vs baseline is computed
      - Model is promoted to canary (5% traffic)
      - After 48 hours, if no regression, promoted to 100% traffic
    And metrics are logged to the audit trail

  @pending
  Scenario: API Contract - POST /v1/conversations/{id}/messages
    Given a valid tenant with API credentials
    
    When a POST request is sent:
      POST /v1/conversations/conv-123/messages
      Idempotency-Key: \"key-123-abc\"
      Content-Type: application/json
      
      {
        \"sender_id\": \"cust-456\",
        \"body\": \"Where's my order?\",
        \"channel_id\": \"ch-web-chat\"
      }
    
    Then the response is 202 Accepted (not 201) with:
      {
        \"message_id\": \"msg-789\",
        \"stream_url\": \"https://api.triage.local/v1/streams/conversations/conv-123\",
        \"status\": \"processing\"
      }
    And the response includes an SSE stream URL
    And a second POST with the same Idempotency-Key returns 409 Conflict (idempotency enforced)
    And the message is durable (survives crash)

  @pending
  Scenario: Tenant Isolation - RLS Enforcement
    Given two tenants: \"tenant-a\" and \"tenant-b\"
    And each tenant has conversations and messages
    
    When a query is executed as \"tenant-a\"
    Then only conversations and messages for \"tenant-a\" are visible
    And conversations for \"tenant-b\" return zero rows
    And the database RLS policy is enforced at the row level
    
    When a query is attempted without setting app.tenant_id context
    Then the query fails with TenantContextError

  @pending
  Scenario: Audit Log Tamper Detection
    Given an audit log with 3 entries forming a hash chain
    
    When an auditor retrieves all entries and verifies the chain
    Then all hashes are valid and link correctly
    
    When an attacker attempts to modify entry 1 (change action from \"create\" to \"delete\")
    Then the hash of entry 1 changes
    And entry 2's previous_hash no longer matches entry 1's new hash
    And chain verification fails with message: \"previous_hash broken at entry 2\"
```

## Acceptance Test Structure

**Feature Files:**
- Located in `tests/acceptance/features/`
- Written in Gherkin (readable by business stakeholders)
- Marked `@pending` initially (expected to fail)
- Progress tracked: count passing scenarios

**Step Definitions:**
- Located in `tests/acceptance/steps/`
- Implement Gherkin steps
- Reference fixtures for setup (tenants, channels, integrations)

**Running:**
```bash
# All acceptance scenarios (most fail - expected)
pytest tests/acceptance/ -v

# Only passing scenarios
pytest tests/acceptance/ -v -m \"not pending\"

# Specific scenario
pytest tests/acceptance/features/scenarios.feature -k \"J1\" -v
```
