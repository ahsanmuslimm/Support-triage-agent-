# S4.2 — Proactive Outreach Triggers

## Overview

**Purpose:** Automatically identify customers needing proactive support before they contact support channels, reducing inbound volume and improving customer satisfaction by addressing issues at early warning signs.

**Business Value:**
- Reduce support ticket volume by 15–25% through early intervention
- Improve NPS by 10–15 points via timely, relevant outreach
- Increase upsell/cross-sell opportunities through health-aware targeting
- Lower churn rate by 8–12% for high-risk segments

**Integration with S4.1 (Anomaly Signals):**
S4.2 consumes anomaly scores and customer health snapshots produced by S4.1, triggering campaigns when health metrics cross configured thresholds. Trigger evaluation happens post-anomaly detection, applying business logic to route customers to outreach workflows rather than support escalations.

## Technical Specification

### Four Trigger Types

**1. Health Score Degradation**
- **Condition:** `health_score < threshold` (configurable per tenant; default 60/100)
- **Detection window:** Daily snapshot comparison
- **Action:** Queue outreach campaign, log trigger event
- **Example:** Customer health drops from 75 → 52 in 24 hours → tier-2 support outreach

**2. Engagement Drop**
- **Condition:** `days_since_last_login > inactivity_threshold` OR `days_since_last_purchase > purchase_threshold`
- **Inactivity threshold:** Default 14 days (configurable)
- **Purchase threshold:** Default 30 days (B2C) / 60 days (B2B)
- **Action:** Send re-engagement email, in-app notification
- **Example:** SaaS user inactive 21 days → "We miss you" campaign + feature discovery email

**3. Billing Issues**
- **Conditions:**
  - Failed payment (3+ consecutive failures)
  - Card expiry within 7 days
  - Subscription renewal date at risk (payment method invalid)
  - Usage-based overage warning (80%+ of account limit)
- **Grace period:** 24 hours before dunning campaign
- **Action:** Billing support outreach, upsell alternative plan
- **Example:** Credit card expires in 5 days → proactive update reminder

**4. Loyalty Milestone**
- **Conditions:**
  - VIP tier upgrade or downgrade
  - Churn risk crossing threshold (risk_score > 0.75)
  - Contract renewal approaching (30 days out)
  - Anniversary-based loyalty rewards
- **Action:** VIP onboarding, win-back campaign, renewal negotiation
- **Example:** Customer risks downgrade → dedicated account manager outreach

### Campaign Delivery

**Batch Scheduler:**
- Celery beat job runs every 6 hours (configurable per tenant)
- Evaluates customer cohorts (1000–5000 per batch)
- Deduplicates via idempotency key: `hash(customer_id + trigger_type + date)`
- Retries failed deliveries with exponential backoff (5m, 15m, 1h, 24h)

**Email Channel:**
- Template mapping: `trigger_type → email_template_id`
- SMTP provider: SendGrid (or configurable)
- Unsubscribe compliance: links in footer, list preference checks
- Delivery status tracking: sent, opened, clicked, bounced, complained

**In-App Notification Channel:**
- HTTP POST to customer app webhook (with retry logic)
- Fallback to push notification via Firebase Cloud Messaging
- Dismiss tracking, conversion logging
- Banner, modal, or toast UI presentation (template configurable)

### A/B Testing Framework

**Control/Variant Assignment:**
- Deterministic: `variant = (hash(customer_id + campaign_id) % 100) < variant_split_percentage`
- **Variant split:** Configurable; typically 50/50 control/treatment
- **Holdout group:** 20% of assigned customers (control only, no treatment)
- **Stratification:** By health_score tier, customer segment, region

**Metrics Tracked:**
- Conversion rate (outreach → support ticket / purchase)
- Click-through rate (email links)
- Open rate (email), dismissal rate (in-app)
- Revenue impact (holdout vs. variant)
- **Significance testing:** Chi-squared test at p < 0.05

## Implementation

### Health Score Computation

**Formula (weighted average):**
```
health_score = (
  0.40 × product_usage_score +
  0.30 × support_satisfaction_score +
  0.20 × nps_score +
  0.10 × billing_health_score
)
```

**Product usage score** (0–100):
```
usage_score = min(100, (
  (active_days_last_30 / 30) × 40 +
  (feature_adoption_breadth / total_features) × 40 +
  (session_frequency_normalized) × 20
))
```

**Support satisfaction score:**
- CSAT average from last 5 closed tickets (0–100)
- Decays by 5 points per unresolved ticket > 7 days old

**NPS score:**
- Most recent NPS response (0–100 from 0–10 scale)
- Weighted by recency; defaults to 50 if no recent survey

**Billing health score:**
- 100 if active subscription, valid payment method, current invoice paid
- Deduct 30 if payment method expiring within 30 days
- Deduct 50 if payment failed in last 7 days
- Deduct 60 if past due balance > 0

### Engagement Drop Detection

**Activity event tracking** (Redis sorted set per customer):
```python
redis_key = f"activity:{tenant_id}:{customer_id}"
# On each activity event (login, purchase, API call):
redis.zadd(redis_key, {timestamp: event_type})
redis.expire(redis_key, 86400 * 90)  # Keep 90 days
```

**Inactivity query:**
```python
now = time.time()
last_event_ts = redis.zrevrange(redis_key, 0, 0, withscores=True)
if last_event_ts:
  inactivity_seconds = now - last_event_ts[0][1]
  inactivity_days = inactivity_seconds / 86400
  return inactivity_days > threshold_days
```

### Campaign Scheduler

**Celery beat task** (`tasks.py`):
```python
from celery.beat import ScheduleEntry
from celery import shared_task

@shared_task
def evaluate_and_dispatch_campaigns():
  """Run every 6 hours; enumerates all active CampaignSchedules."""
  schedules = CampaignSchedule.objects.filter(enabled=True)
  
  for schedule in schedules:
    # Check if cron expression matches current time
    if not should_run_now(schedule.schedule_cron):
      continue
    
    # Fetch candidate customers
    candidates = get_trigger_candidates(
      schedule.trigger_type,
      schedule.target_audience
    )
    
    for batch in chunks(candidates, 1000):
      dispatch_batch.delay(schedule.id, batch)

@shared_task
def dispatch_batch(schedule_id, customer_ids):
  """Send campaign to a batch of customers; apply A/B assignment."""
  schedule = CampaignSchedule.objects.get(id=schedule_id)
  
  for customer_id in customer_ids:
    # Deduplication key prevents duplicate sends within 24h
    dedup_key = f"{customer_id}:{schedule.trigger_type}:{date.today()}"
    if cache.get(dedup_key):
      continue
    
    # A/B assignment
    variant = hash_variant(customer_id, schedule.id, schedule.ab_variant)
    template_id = (
      schedule.ab_variant['variant_template_id']
      if variant == 'treatment' else
      schedule.ab_variant['control_template_id']
    )
    
    send_campaign(schedule, customer_id, template_id)
    cache.set(dedup_key, True, ttl=86400)
```

### A/B Assignment (Deterministic)

```python
def hash_variant(customer_id: str, campaign_id: str, ab_config: dict) -> str:
  """
  Deterministic assignment based on customer_id + campaign_id.
  Returns 'control', 'treatment', or 'holdout'.
  """
  combined = f"{customer_id}:{campaign_id}"
  hash_value = int(hashlib.md5(combined.encode()).hexdigest(), 16)
  bucket = hash_value % 100
  
  split = ab_config['split_percentage']
  holdout = ab_config.get('holdout_percentage', 0)
  
  if bucket < holdout:
    return 'holdout'
  elif bucket < holdout + (split // 2):
    return 'control'
  else:
    return 'treatment'
```

### A/B Assignment Tests

```python
def test_ab_assignment_deterministic():
  """Same customer + campaign always gets same variant."""
  customer_id = "cust_001"
  campaign_id = "camp_001"
  
  variant1 = hash_variant(customer_id, campaign_id, ab_config)
  variant2 = hash_variant(customer_id, campaign_id, ab_config)
  
  assert variant1 == variant2

def test_ab_distribution(sample_size=10000):
  """Verify 50% control / 50% treatment distribution."""
  ab_config = {'split_percentage': 50, 'holdout_percentage': 20}
  
  control_count = sum(
    1 for i in range(sample_size)
    if hash_variant(f"cust_{i}", "camp_test", ab_config) == 'control'
  )
  
  # Chi-squared test: observed ≈ expected (with tolerance)
  expected = sample_size * 0.40  # 40% after accounting for 20% holdout
  chi2 = ((control_count - expected) ** 2) / expected
  
  assert chi2 < 3.84  # Critical value at p=0.05, df=1
```

- **Celery broker:** Redis (handles 10k+ triggers/hour)

- **Observability:** Prometheus metrics, structured logging (JSON)

## Summary

S4.2 implements a four-trigger proactive outreach system with deterministic A/B testing and batch campaign scheduling. Health score degradation, engagement drop, billing issues, and loyalty milestones drive targeted customer interventions via email and in-app channels, reducing support inbound and improving retention.
