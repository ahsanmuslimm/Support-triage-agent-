# S4.4 — Operations Dashboard

## Overview

Real-time operations dashboard for support managers enables live monitoring and intervention across the triage platform. The dashboard provides visibility into agent performance metrics, anomaly detection alerts, manual override queue management, and dynamic team workload distribution. Managers can acknowledge alerts, assign work, and escalate conversations in real time via a React-based frontend backed by WebSocket streaming and Prometheus metrics aggregation.

## Technical Specification

### Dashboard Panels

#### 1. Real-Time Agent Performance
- **Accuracy**: Percentage of correct triage classifications (model-predicted vs. manual override ground truth)
- **Escalation Rate**: Escalations per agent per hour; threshold alert at >15%
- **Latency Metrics**:
  - p50 (median response time): target <2s
  - p95: target <5s
  - p99: target <10s
- Visualization: Line charts with rolling 1h/4h/24h windows; color-coded (green <target, yellow at-risk, red exceeded)

#### 2. Anomaly Alerts
Integrated alerts from S4.1 spike detector and model drift monitoring:
- High escalation spike (>3σ deviation)
- Model drift indicator: validation accuracy drop >5% vs. baseline
- Queue saturation: >80% capacity utilization
- Agent offline: no activity for >5 min
- Severity levels: info, warning, critical
- Actionable: one-click acknowledge, drill-down to affected conversations

#### 3. Manual Override Queue
- Sortable columns: priority (high/medium/low), age, agent assigned, reason, status
- Server-side pagination (20 per page, optimized for large queues)
- Bulk actions: bulk assign to team, bulk escalate, bulk mark reviewed
- Status lifecycle: pending → acknowledged → resolved/escalated
- Right-click context menu: assign, escalate, view conversation details

#### 4. Team Assignments & Workload Heatmap
- Agent grid: name, queue depth, active conversations, avg handle time, SLA at-risk count
- Color heatmap: green (light load), yellow (balanced), red (overloaded)
- SLA countdown: agents with conversations nearing SLA threshold flagged
- Bulk rebalancing: "Auto-assign pending" button triggers workload leveler

### Technology Stack

**Frontend**: React 18+ with TypeScript; real-time state via WebSocket; Recharts for metrics visualization

**Backend**: Python FastAPI; async WebSocket server via `websockets` or `starlette.websockets`; per-tenant broadcast rooms

**Metrics**: Prometheus scraped every 15s; Grafana for historical trending and alert rule definitions; API aggregation layer for instant snapshots

**Infrastructure**: WebSocket server as separate uvicorn process; Nginx reverse proxy with sticky sessions (`ip_hash` or `jsessionid`)

## Implementation

### Metrics Aggregation Pipeline
1. **Prometheus Scrape**: Agent service exposes `/metrics` endpoint (Starlette prometheus middleware); Prometheus config scrapes every 15s
2. **Grafana Dashboard**: Pre-provisioned JSON dashboard config (infrastructure-as-code) displays time-series with alerting rules
3. **API Aggregation Layer**: FastAPI endpoint aggregates latest Prometheus data, calculates percentiles, and returns JSON snapshot

```python
async def get_dashboard_metrics(tenant_id: str):
    prom_query = 'agent_accuracy{tenant_id="' + tenant_id + '"}'
    result = prometheus_client.query(prom_query)
    aggregated = calculate_percentiles(result)
    return aggregated
```

### WebSocket Server Architecture
- **Per-tenant rooms**: Each tenant gets isolated broadcast room; managers subscribe to their tenant's room
- **Sticky sessions**: Nginx reverse proxy routes all WS requests for a session to same uvicorn instance via `ip_hash`
- **Heartbeat**: Server sends ping every 30s; client auto-reconnects on timeout
- **Metric delta publishing**: Every 5s, calculate delta from last snapshot, broadcast to room subscribers

```python
class DashboardWSManager:
    def __init__(self):
        self.rooms = {}  # tenant_id -> set(ConnectionManager)
    
    async def broadcast_metrics(self, tenant_id: str, metrics: dict):
        room = self.rooms.get(tenant_id, set())
        for conn in room:
            await conn.send_json({
                "type": "metric_update",
                "timestamp": datetime.utcnow().isoformat(),
                "metrics": metrics
            })
```

### Override Queue: Sorting & Pagination
- **Server-side sort**: Multi-key sort by (priority DESC, created_at ASC); Postgres `ORDER BY` clause
- **Pagination**: Offset/limit pattern; limit enforced to 100 max per request
- **Indexing**: Composite index on (tenant_id, status, created_at) for fast queries

```sql
SELECT * FROM manual_overrides
WHERE tenant_id = %s AND status = 'pending'
ORDER BY priority DESC, created_at ASC
LIMIT %s OFFSET %s;
```

### Bulk Actions: Transactional Atomicity
- All bulk operations wrapped in database transaction; either all succeed or all rollback
- Workload leveler algorithm: assign overrides to agent with lowest current queue_depth

```python
async def bulk_assign_overrides(override_ids: list, target_agent_id: str, tenant_id: str):
    async with db.transaction():
        for override_id in override_ids:
            await db.execute("""
                UPDATE manual_overrides 
                SET assigned_to_agent = %s, updated_at = NOW()
                WHERE id = %s AND tenant_id = %s
            """, target_agent_id, override_id, tenant_id)
        # Emit events for real-time broadcast
        await ws_manager.broadcast_alert(tenant_id, {
            "type": "overrides_assigned",
            "count": len(override_ids)
        })
```

### Alert Acknowledgment
- Sets `acknowledged_at` timestamp and `acknowledged_by` manager ID
- Removes from "active alerts" cache; retained in audit log for compliance
- Triggers event for real-time dashboard update (alert disappears from manager's UI)

### Workload Rebalancing Algorithm
Greedy algorithm: iterate pending overrides sorted by created_at, assign each to agent with lowest queue_depth

```python
def calculate_workload_rebalancing(agents: list, pending_overrides: int) -> dict:
    avg_load = sum(a.queue_depth for a in agents) / len(agents)
    underloaded = [a for a in agents if a.queue_depth < avg_load * 0.8]
    overloaded = [a for a in agents if a.queue_depth > avg_load * 1.3]
    
    moves = []
    for override in pending_overrides[:len(underloaded)]:
        target = min(underloaded, key=lambda a: a.queue_depth)
        moves.append({"override_id": override.id, "to_agent": target.agent_id})
    
    return {"recommended_moves": moves}
```

## Testing Strategy

### Unit Tests: Metrics Calculation
- Verify aggregation logic: team_accuracy = mean(individual accuracies)
- Percentile calculation: feed sorted latency array, assert p50/p95/p99 values
- Edge case: zero agents online, empty conversation queue

### Integration Tests: Alert Triggers
- Inject synthetic spike (high escalation % for agent)
- Poll `/api/v1/dashboard/alerts` every 100ms for up to 2s
- Assert new alert appears with correct alert_type and severity within SLA

### Integration Tests: Team Assignment Logic
- Populate 3 agents with varying queue depths (2, 5, 10 conversations)
- Call workload rebalancing; verify algorithm recommends moving conversations from agent 3 to agent 1
- Unit test: verify atomicity of bulk assignment (if one insert fails, transaction rolls back)

### WebSocket Integration Tests
- Establish WS connection to /ws/dashboard
- Trigger metric update in backend (e.g., escalation spike)
- Assert message received on WS client within 5s with correct payload
- Disconnect and reconnect; verify no message loss (use sequence numbers)

### Grafana Panel Tests
- Validate JSON panel configs render without errors
- Spot-check metric queries return non-null data
- Verify alert rule thresholds are correctly wired (e.g., escalation_rate > 0.15 triggers critical alert)

## Summary

The Operations Dashboard delivers real-time visibility and intervention capabilities for support managers. Sticky sessions and per-tenant WebSocket rooms ensure scalability and isolation. Integration with S4.1 anomaly detection creates a unified alert ecosystem.
