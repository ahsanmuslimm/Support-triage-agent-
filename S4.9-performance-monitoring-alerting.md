# S4.9 — Performance Monitoring & Alerting

## Overview

Full observability stack for the support triage platform, enabling real-time KPI tracking, operational dashboards for SREs, automated alert rules with intelligent thresholds, and runbooks for incident response. This sprint delivers Prometheus metrics collection, Grafana dashboards, AlertManager routing, and documented runbooks for common escalation scenarios.

---

## Technical Specification

### 1. Key Performance Indicators (KPIs)

**Primary KPIs:**
- **Escalation Rate**: Percentage of triage requests escalated to human agents (target: <15%)
- **Resolution Time (p50/p95/p99)**: Seconds from ticket creation to resolution (target: p95 < 120s for automated, p95 < 600s for escalated)
- **Customer Satisfaction Score (CSAT)**: Rolling 7-day average NPS/post-resolution survey (target: >8.0)
- **Cost Per Resolution**: USD spent on inference + human review per resolved ticket (target: <$0.50)
- **Model Accuracy**: Intent classification F1-score per model version (target: >0.92)
- **SLA Breach Rate**: Percentage of tickets missing priority-based SLA window (P1: 30min, P2: 2h, P3: 24h) (target: <2%)

### 2. Grafana Dashboards

Four dashboards for different audiences:

**Dashboard A: Overview (Executive/SRE)**
- Escalation rate 15-min trend (line chart, threshold line at 20%)
- Resolution time p95 (gauge, green <120s, yellow <180s, red >180s)
- CSAT rolling average (gauge, green >8.0, yellow 7.0-8.0, red <7.0)
- Inference latency p95 (gauge, threshold 2s)
- Model accuracy trend by version (line chart)
- Alert status (row with red/yellow/green status indicators)

**Dashboard B: Triage Performance (Data Science)**
- Intent distribution pie chart (top 10 intents by volume)
- Latency histogram by intent (heatmap, percentiles 50/95/99)
- Accuracy by model version (bar chart)
- Confidence score distribution (histogram, bins: 0.0-0.5, 0.5-0.7, 0.7-0.9, 0.9-1.0)
- False positive rate trend (line)
- Inference duration distribution (percentiles table)

**Dashboard C: Escalation Queue (Operations)**
- Queue depth by priority (stacked bar, P1/P2/P3)
- SLA time remaining heatmap (rows=tickets, col=minutes remaining, color=red/yellow/green)
- Escalation breach rate (gauge)
- Top escalation reasons (bar chart, top 5)
- Wait time for first agent response (gauge)
- Escalation-to-resolution time p95 (gauge)

**Dashboard D: Anomaly Signals (Platform Ops)**
- Signal frequency by type (bar chart: drift, latency_spike, accuracy_drop, volume_spike)
- Detection latency distribution (histogram)
- Signal timeline (annotation on escalation rate)
- Correlation matrix: model_drift vs escalation_rate (scatter)
- System resource usage (CPU, memory, GPU utilization)

## Metrics Catalog

All metrics use namespace `support_triage_` and are collected at 15-second intervals.

| Metric Name | Type | Labels | Description |
|---|---|---|---|
| `support_triage_requests_total` | Counter | `tenant_id`, `intent`, `status` (auto/escalated/failed) | Total triage requests processed |
| `support_triage_requests_duration_seconds` | Histogram | `tenant_id`, `intent`, `status` | End-to-end triage latency (buckets: 0.05, 0.1, 0.2, 0.5, 1.0, 2.0, 5.0, 10.0) |
| `support_triage_escalation_rate` | Gauge | `tenant_id` | (escalations / total_requests) over rolling 15-min window |
| `support_triage_resolution_time_seconds` | Histogram | `tenant_id`, `priority` (P1/P2/P3), `method` (auto/manual) | Time from ticket creation to resolution |
| `support_triage_customer_satisfaction_score` | Gauge | `tenant_id` | Rolling 7-day average CSAT/NPS (0–10 scale) |
| `support_triage_model_accuracy` | Gauge | `tenant_id`, `model_version`, `metric` (f1/precision/recall) | Intent classification accuracy metrics |
| `support_triage_sla_breach_rate` | Gauge | `tenant_id`, `priority` | Percentage of tickets breaching SLA |
| `support_triage_anomaly_signals_total` | Counter | `tenant_id`, `signal_type` (drift/latency_spike/accuracy_drop/volume_spike) | Anomaly detection triggers |
| `support_triage_inference_latency_seconds` | Histogram | `tenant_id`, `model_name` | Model inference duration (buckets: 0.01, 0.05, 0.1, 0.5, 1.0, 2.0) |
| `support_triage_queue_depth` | Gauge | `tenant_id`, `priority` | Count of tickets awaiting human agent |

## Runbooks

### Runbook: Escalation Rate Spike

**When This Alert Fires:**
- Escalation rate has increased >20% from 60-minute baseline, sustained for 15 minutes
- Typically indicates degradation in triage accuracy, system outage, or anomalous user behavior

**Diagnosis Steps:**

1. **Verify Alert Legitimacy**
   - Check Grafana Overview dashboard: is escalation rate actually spiking?
   - Confirm no scheduled maintenance or data pipeline issues in last 2 hours
   - Query: `SELECT count(*), avg(escalation_flag) FROM tickets WHERE created_at > NOW() - INTERVAL 1 HOUR GROUP BY created_at_bucket(5 MINUTES)`

2. **Check Model Health**
   - Run: `kubectl logs -n triage deployment/intent-classifier --tail=200 | grep -i error`
   - Check model accuracy gauge: `support_triage_model_accuracy{metric="f1", tenant_id="<tenant>"}`
   - If accuracy <0.90, trigger `ModelAccuracyDrop` diagnostic separately

3. **Review Escalation Reasons**
   - Query dashboard: "Escalation Queue" panel → "Top escalation reasons"
   - If >60% are single reason, investigate that code path
   - Example: if "confidence_below_threshold" dominates, check model output distribution (may indicate data drift)

4. **Check System Resources**
   - CPU/memory on inference pods: `kubectl top pod -n triage | grep intent-classifier`
   - GPU utilization: `nvidia-smi` (on inference nodes)
   - If >90% utilization, scaling is needed

5. **Review Recent Deployments**
   - `git log --oneline -20 --since="2 hours ago" -- triage/`
   - Check deployment timestamps: `kubectl rollout history deployment/triage-engine -n triage`
   - If recent deploy correlates with spike, consider rollback

**Remediation Options:**

- **Option A: Immediate mitigation (no rollback)**
  1. Scale up escalation agent pool: `kubectl scale deployment escalation-handler --replicas=20 -n triage`
  2. Reduce triage timeout from 5s to 2s (sends more to escalation)
  3. Temporarily disable low-confidence predictions (<0.70) → escalate automatically
  4. Monitor SLA breach rate (may worsen due to larger queue)

- **Option B: Rollback recent change (if deployment correlates)**
  1. `kubectl rollout undo deployment/triage-engine -n triage`
  2. Verify escalation rate returns to baseline within 15 minutes
  3. Post-incident review of failed deployment

- **Option C: Model retraining (if accuracy degradation detected)**
  1. Run: `python scripts/retrain_intent_classifier.py --dataset=recent_30d --output=model_v2.5`
  2. Evaluate on holdout test set
  3. A/B test: deploy to 5% traffic, monitor accuracy + escalation rate for 1 hour
  4. If successful, gradual rollout to 100%

**Escalation Path:**
- If not resolved in 15 min: page on-call ML Engineer (PagerDuty: ml-platform-oncall)
- If not resolved in 30 min: page infrastructure SRE to assess resource constraints or systematic failures
- If customer impact confirmed: notify support leadership; consider manual escalation override to reduce queue backlog

### Runbook: Inference Latency Degradation

**When This Alert Fires:**
- p95 inference latency exceeds 2 seconds for 10+ minutes
- Typically indicates resource contention, model size issue, or service dependency degradation

**Diagnosis Steps:**

1. **Check Inference Service Health**
   - Verify service is running: `kubectl get pods -n triage -l app=inference-service`
   - Check readiness probes: `kubectl describe pod <pod-name> -n triage | grep -A 5 "Readiness"`
   - Review service logs: `kubectl logs -n triage deployment/inference-service --tail=500 | tail -100`

2. **Assess Resource Utilization**
   - CPU/memory: `kubectl top pod -n triage -l app=inference-service --containers`
   - GPU utilization on each node: `nvidia-smi` (if GPU-enabled)
   - Disk I/O on model storage: `iostat -x 1 10`
   - If CPU >80% or GPU >85%, scaling is needed

3. **Check Model Loading**
   - Verify model is in cache: `ls -lh /models/intent-classifier-v2.4.onnx`
   - Check model file size (if >2GB, may cause slow disk reads): `du -h /models/*`
   - Verify PyTorch/ONNX runtime version: `python -c "import onnxruntime; print(onnxruntime.__version__)"`

4. **Trace Latency Components**
   - Request: `kubectl logs deployment/inference-service | grep "duration_ms"`
   - Sample latencies: tokenization, embedding, inference, post-processing
   - Identify bottleneck: if embedding >1.5s, may be embedding service issue; if inference >1.0s, may be model/GPU issue

5. **Check Dependent Services**
   - Embedding service: `curl -I http://embedding-service:8080/health` (should return 200)
   - Redis cache availability: `redis-cli -h redis.triage ping` (should return PONG)
   - Database connection pool: `kubectl logs deployment/inference-service | grep "pool_size\|connections"`

**Remediation Options:**

- **Option A: Scale horizontally**
  1. `kubectl scale deployment/inference-service --replicas=5 -n triage` (default: 3)
  2. Load balancer will distribute traffic across replicas
  3. Monitor: `kubectl top pod -n triage -l app=inference-service --containers` should show ~30% per pod

- **Option B: Optimize model serving**
  1. Enable quantization: `export MODEL_QUANTIZE=int8` in Deployment
  2. Reduce batch size if batching enabled: `export BATCH_SIZE=8` (default: 16)
  3. Redeploy: `kubectl rollout restart deployment/inference-service -n triage`

- **Option C: Upgrade hardware or model architecture**
  1. If GPU consistently at >85%: request GPU node scaling (infra team)
  2. Evaluate lightweight model variant: `scripts/convert_to_distilled_model.py --model=v2.4 --output=v2.4-distilled`
  3. A/B test distilled model: latency should improve by 30–40%

**Escalation Path:**
- If not resolved in 10 min: page on-call platform SRE (infrastructure/Kubernetes expert)
- If latency returns to normal but root cause unknown: trigger post-incident review to document findings
- If customer SLAs breached: notify support + finance (cost of compensation, if applicable)

### Runbook: Model Accuracy Drop

**When This Alert Fires:**
- Intent classification F1-score drops below 0.92 AND declines >5% in 1 hour
- Indicates data drift, adversarial inputs, or model degradation

**Diagnosis Steps:**

1. **Confirm Accuracy Metric**
   - Source: labeled validation set or held-out test set?
   - Query: `SELECT avg(f1_score) FROM model_evaluations WHERE created_at > NOW() - INTERVAL 1 HOUR`
   - Compare: current F1 vs. baseline (should be tracked in Prometheus)

2. **Check Data Distribution Shift**
   - Sample recent tickets (last 1 hour): `SELECT intent, count(*) FROM tickets WHERE created_at > NOW() - INTERVAL 1 HOUR GROUP BY intent`
   - Compare to historical baseline (last 7 days)
   - Are new intents appearing? Is one intent volume >50% of traffic (may indicate data drift)?

3. **Analyze Failure Patterns**
   - Query misclassified examples: `SELECT id, text, predicted_intent, actual_intent FROM tickets WHERE correct_prediction=false AND created_at > NOW() - INTERVAL 1 HOUR LIMIT 50`
   - Are failures clustered by intent, text length, or language?
   - Use embedding visualization tool to detect outliers in feature space

4. **Review Recent Changes**
   - Check model version deployed: `kubectl get deployment triage-engine -n triage -o json | jq '.spec.template.spec.containers[0].env[] | select(.name=="MODEL_VERSION")'`
   - Compare to prior version: `git diff v2.3..v2.4 -- models/intent_classifier.py`
   - Training data changes: `git log --oneline -5 -- data/training_labels.csv`

5. **Check Model Calibration**
   - Review confidence score distribution: histogram from Grafana "Triage Performance" dashboard
   - If median confidence <0.75, model is uncertain (may need retraining)
   - If confidence distribution has sudden spikes/gaps, may indicate training data issue

**Remediation Options:**

- **Option A: Rollback to previous model**
  1. Identify last-known-good model: `kubectl rollout history deployment/triage-engine -n triage`
  2. Rollback: `kubectl rollout undo deployment/triage-engine -n triage`
  3. Verify accuracy recovers: monitor `support_triage_model_accuracy` gauge for 30 minutes
  4. Post-incident: investigate why v2.4 degraded

- **Option B: Emergency retraining on recent data**
  1. Collect recent labeled data (last 7 days): `python scripts/export_recent_labels.py --output=recent_7d.csv --limit=50000`
  2. Inspect for label quality issues: `python scripts/validate_labels.py recent_7d.csv`
  3. Retrain: `python scripts/train_intent_classifier.py --dataset=recent_7d.csv --output=model_v2.4-hotfix`
  4. Evaluate on held-out test set: `python scripts/evaluate_model.py --model=v2.4-hotfix --test_set=test.csv`
  5. If F1 >0.92 on test set, deploy as canary: 5% traffic for 1 hour, then gradual rollout

- **Option C: Threshold adjustment (temporary mitigation)**
  1. Increase confidence threshold for auto-resolution: `export MIN_CONFIDENCE=0.85` (default: 0.75)
  2. Lower-confidence predictions routed to escalation
  3. Escalation rate will increase temporarily, but accuracy improves
  4. Monitor SLA breach rate (may worsen)

**Escalation Path:**
- If not resolved in 30 min: page on-call ML Engineer
- If data quality issues found: escalate to data engineering team to audit labeling pipeline
- If systematic model degradation: trigger model retraining task (may take 2–4 hours)

### Runbook: SLA Breach Rate High (P1)

**When This Alert Fires:**
- >5% of P1 tickets are exceeding 30-minute resolution SLA for 5+ minutes
- Indicates escalation queue backlog or human agent availability issue

**Diagnosis Steps:**

1. **Confirm Queue Status**
   - Current queue depth: `SELECT count(*) FROM tickets WHERE priority='P1' AND assigned_agent IS NULL`
   - Average wait time: `SELECT avg(EXTRACT(EPOCH FROM (agent_assigned_at - created_at))) FROM tickets WHERE priority='P1' AND created_at > NOW() - INTERVAL 1 HOUR`
   - Dashboard: check "Escalation Queue" panel for visual confirmation

2. **Check Agent Availability**
   - Agents online: `SELECT count(DISTINCT agent_id) FROM agent_sessions WHERE logged_out_at IS NULL`
   - Agents idle (not handling ticket): `SELECT count(*) FROM agent_sessions WHERE logged_out_at IS NULL AND current_ticket_id IS NULL`
   - Avg handling time: `SELECT avg(EXTRACT(EPOCH FROM (closed_at - assigned_at))) FROM tickets WHERE priority='P1' AND closed_at > NOW() - INTERVAL 1 HOUR`

3. **Review Ticket Volume Spike**
   - Tickets created in last 1 hour: `SELECT count(*) FROM tickets WHERE created_at > NOW() - INTERVAL 1 HOUR`
   - Compare to 7-day average: `SELECT avg(daily_count) FROM (SELECT count(*) as daily_count FROM tickets WHERE created_at > NOW() - INTERVAL 7 DAYS GROUP BY DATE(created_at)) t`
   - If inbound spike >30%, may be legitimate surge

4. **Assess System Health**
   - Triage service latency: is inference working? (check inference latency alert)
   - Escalation queue service errors: `kubectl logs deployment/escalation-queue -n triage | grep ERROR | tail -20`
   - Database slow queries: check slow query log for SELECT/UPDATE statements on tickets table

5. **Check Staffing Schedule**
   - Is this during off-hours or low-staffing period?
   - Compare breach rate to agent count: should correlate
   - Review scheduled PTO: are key agents absent?

**Remediation Options:**

- **Option A: Activate escalation protocol / call-in**
  1. Notify support leadership: P1 queue breaching SLA
  2. Activate on-call rotation or call-in program
  3. Alert support team leads: `curl -X POST http://slack-webhook/channels/support-ops -d '{...}'`
  4. Monitor queue depth every 5 min; update status until resolved

- **Option B: Reduce triage latency to buy time**
  1. Temporarily reduce model confidence threshold: `export MIN_CONFIDENCE=0.65` (from 0.75)
  2. Auto-resolve more tickets, reduce escalations → reduces queue pressure
  3. Tradeoff: escalation rate will drop, but accuracy may suffer (requires monitoring)
  4. Revert once queue is clear

- **Option C: Prioritize queue (triage adjustments)**
  1. Implement urgent-priority queue bypass: tickets with "customer VIP" or "revenue >$100k" get fast-track
  2. Implement urgency re-scoring: sort by time-in-queue + priority + business value
  3. Auto-assign tickets to idle agents (if not already doing so)

**Escalation Path:**
- Immediate: notify support manager and SRE on-call
- If not resolved in 15 min: escalate to VP of Support for staffing decisions
- If repeated pattern: post-incident review to adjust staffing model or automation rules

```bash
  "runbooks/sla-breach-rate.md"
)

for runbook in "${RUNBOOKS[@]}"; do
  echo "Validating: $runbook"
  
  # Check: all kubectl commands are current
  grep -o "kubectl [a-z-]*" "$runbook" | sort -u | while read cmd; do
    kubectl $cmd --help > /dev/null 2>&1 || echo "STALE: $cmd in $runbook"
  done
  
  # Check: all scripts referenced exist
  grep -o "scripts/[a-z_]*\.py" "$runbook" | sort -u | while read script; do
    [ -f "$script" ] || echo "MISSING: $script referenced in $runbook"
  done
  
  # Check: Slack/PagerDuty webhook URLs are documented (not hardcoded)
  grep -E "http.*slack|http.*pagerduty" "$runbook" && \
    echo "WARNING: Webhooks may be hardcoded in $runbook (should use env vars)"
  
  echo "✓ $runbook validated"
done
```

```yaml
# manifests/alertmanager-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: alertmanager-config
  namespace: monitoring
data:
  config.yml: |
    global:
      resolve_timeout: 5m
      slack_api_url: '${ALERTMANAGER_SLACK_WEBHOOK}'
      pagerduty_url: 'https://events.pagerduty.com/v2/enqueue'
    
    route:
      receiver: 'default'
      group_by: ['alertname', 'cluster', 'service']
      group_wait: 10s
      group_interval: 10s
      repeat_interval: 12h
      
      routes:
        - match:
            severity: critical
            component: triage-engine
          receiver: 'critical-escalation'
          continue: true
          group_wait: 0s
          repeat_interval: 1m
        
        - match:
            severity: warning
            team: platform-ops
          receiver: 'ops-slack'
          group_wait: 30s
        
        - match:
            severity: warning
          receiver: 'default-slack'
    
    receivers:
      - name: 'default'
        slack_configs:
          - channel: '#alerts'
            title: '{{ .GroupLabels.alertname }}'
            text: '{{ range .Alerts }}{{ .Annotations.description }}{{ end }}'
      
      - name: 'critical-escalation'
        slack_configs:
          - channel: '#critical-alerts'
            title: '🚨 CRITICAL: {{ .GroupLabels.alertname }}'
        pagerduty_configs:
          - service_key: '${PAGERDUTY_SERVICE_KEY_CRITICAL}'
            description: '{{ .GroupLabels.alertname }}: {{ (index .Alerts 0).Annotations.summary }}'
            links:
              - href: '{{ (index .Alerts 0).Annotations.runbook_url }}'
                text: 'Runbook'
      
      - name: 'ops-slack'
        slack_configs:
          - channel: '#platform-ops'
            title: '⚠️ {{ .GroupLabels.alertname }}'
    
    inhibit_rules:
      # Don't alert on latency if service is down
      - source_match:
          alertname: 'InferenceServiceDown'
        target_match:
          alertname: 'InferenceLatencyDegradation'
        equal: ['tenant_id']
      
      # Don't alert on escalation spike if inference is broken
      - source_match:
          alertname: 'ModelAccuracyDrop'
        target_match:
          alertname: 'EscalationRateSpike'
        equal: ['tenant_id']
```
