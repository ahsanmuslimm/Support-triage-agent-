## Overview

### What This Delivers

S6.1 defines the foundational Protobuf contracts that serve as the "contract" between producers and consumers in the distributed architecture. All events flowing through Kafka are serialized using these Protobuf definitions.

**Key Artifacts:**
- `buf.yaml` - buf CLI configuration
- `buf.gen.yaml` - code generation configuration for Python & Go
- 4 Protobuf definition files (events.proto, message_events.proto, messages.proto, workflow_inputs.proto)
- Automated code generation pipeline (GitHub Actions)
- Contract tests validating serialization/deserialization

### Design Principles

1. **Protocol Buffers 3** for binary serialization (compact, fast, language-agnostic)
2. **CloudEvents RFC 7807** envelope for metadata (id, source, type, tenant_id)
3. **Multi-tenancy** via tenant_id field in all events
4. **Schema Versioning** for forward/backward compatibility
5. **Partition Key** = tenant_id (for Kafka ordering per tenant)

## Proto Files

### 1. Base Messages (events.proto)

```protobuf
syntax = "proto3";
package triage.events.v1;

import "google/protobuf/timestamp.proto";

// CloudEvents envelope for Kafka (RFC 7807 compatible)
message CloudEvent {
    string id = 1;                                    // UUID
    string source = 2;                               // "triage/messages" (reverse DNS)
    string type = 3;                                 // "message.ingested"
    google.protobuf.Timestamp occurred_at = 4;       // Event time (not wall-clock)
    string content_type = 5;                         // "application/protobuf"
    string data_content_type = 6;                    // "application/protobuf"
    string subject = 7;                              // "tenant/{tenant_id}/message/{message_id}"
    map<string, string> attributes = 8;              // Custom headers
    bytes data = 9;                                  // Serialized payload (e.g., MessageIngested)
    
    // Extensions for multi-tenancy + ordering
    string tenant_id = 100;                          // Partition key
    int32 idempotency_version = 101;                 // For exactly-once
}

// Base event message (all events inherit this pattern)
message BaseEvent {
    string id = 1;                                   // Event ID (UUID)
    string tenant_id = 2;                            // Multi-tenancy
    google.protobuf.Timestamp occurred_at = 3;       // When it happened
    int32 version = 4;                               // Schema version (for evolution)
}
```

**Key Design Decisions:**
- **CloudEvent envelope**: RFC 7807 compatible, wraps domain events
- **BaseEvent reuse**: All domain events inherit base (id, tenant_id, occurred_at, version)
- **Protobuf field numbers**: 1-99 for standard fields, 100+ for extensions
- **Timestamp handling**: google.protobuf.Timestamp for automatic conversion

### 2. Message Events (message_events.proto)

Defines 4 domain event types:
- `MessageIngested` - arrival of message
- `MessageClassified` - NLU classification complete
- `ActionExecuted` - tool execution result
- `MessageEscalated` - human escalation

Each includes classification confidence, sentiment, NLU entities, SLA context.

### 3. Message Domain Model (messages.proto)

Core Message entity with:
- Tenant isolation
- Multi-channel support (email, chat, web)
- Status state machine (INGESTED → CLASSIFIED → ROUTED → RESOLVED)
- Action history
- Timestamp tracking

### 4. Workflow Input (workflow_inputs.proto)

Temporal workflow contracts:
- `ProcessMessageWorkflowInput` - Workflow invocation input
- `WorkflowCheckpoint` - State snapshots (CLASSIFY → ENRICH → DECIDE → RESOLVE)

## Code Generation

### buf Configuration (buf.gen.yaml)

```yaml
outputs:
  - target: go-grpc
    out: gen/go
  
  - target: python
    out: gen/python
    opt:
      - "package_root=gen"
  
  - target: pyi
    out: gen/python
```

**Multi-Target Generation:**
- **Go code** → gen/go/ (for future Go services)
- **Python implementation** (_pb2.py) → gen/python/
- **Python type stubs** (_pb2.pyi) → gen/python/ (for type checkers)

## Usage Example

### Round-Trip Serialization

```python
from gen.python.triage.events.v1 import message_events_pb2, events_pb2

# Create domain event
msg_ingested = message_events_pb2.MessageIngested(
    base=message_events_pb2.BaseEvent(
        id="evt_123",
        tenant_id="tenant_1",
        version=1,
    ),
    message_id="msg_456",
    channel="email",
    body="Where is my order?",
)

# Wrap in CloudEvent
cloud_event = events_pb2.CloudEvent(
    id="evt_123",
    source="triage/messages",
    type="message.ingested",
    tenant_id="tenant_1",
    data=msg_ingested.SerializeToString(),
    data_content_type="application/protobuf",
)

# Serialize to Kafka
kafka_payload = cloud_event.SerializeToString()

# ... transmitted via Kafka ...

# Deserialize on consumer
restored_cloud = events_pb2.CloudEvent()
restored_cloud.ParseFromString(kafka_payload)

# Extract domain event
restored_domain = message_events_pb2.MessageIngested()
restored_domain.ParseFromString(restored_cloud.data)

print(restored_domain.message_id)  # "msg_456"
```

## FAQ

**Q: Why Protobuf instead of JSON?**  
A: Protobuf is 3-10x smaller, faster to serialize/deserialize, and language-agnostic. JSON is used for human-readable logging only.

**Q: How do we handle schema evolution?**  
A: Proto3 provides forward compatibility: new fields are ignored by old consumers, old consumers skip new fields during deserialization.

**Q: What if we need to add a field to MessageIngested?**  
A: Add a new field with next available number (e.g., `int32 field_9 = 9;`). Existing consumers continue working. Regenerate code and deploy. No downtime.

**Q: How do type stubs (.pyi) work?**  
A: Type stubs provide type hints for static analysis tools (mypy, Pyright) without slowing down runtime. Python uses .py files at runtime; type checkers use .pyi files.
