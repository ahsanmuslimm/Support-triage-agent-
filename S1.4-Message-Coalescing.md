## Overview

Message coalescing prevents triage thrashing when customers send multiple messages in rapid succession (typical in chat, not email). It:

1. **Debounces** new messages per conversation (wait 4s for chat, 0s for email)
2. **Locks** conversations during debounce to enforce ordering
3. **Cancels** the debounce if a new message arrives
4. **Releases** the lock when triage completes or heartbeat expires
5. **Handles** "at-node-boundary" cancellation (new message cancels pending triage on old message)

This ensures triage runs on the **complete customer input**, not fragments.

## Technical Specification

### 1. Debouncing Rules by Channel

| Channel | Debounce Duration | Rationale |
|---|---|---|
| **Chat / Web** | 4s | User typically pauses between messages; chat is conversational |
| **Email** | 0s | Each email is discrete; no debounce |
| **SMS / WhatsApp** | 2s | Slightly faster than web chat |
| **Social Media** | 4s | Similar to web chat |
| **Zendesk (comments)** | 0s | Zendesk batches messages server-side |

### 2. Conversation Lock Mechanism

**State Machine:**

```
[UNLOCKED]
    ↓
    → POST /messages → Acquire Lock
    ↓
[LOCKED] (expires in 30s)
    ↓
    → Debounce timer fires (4s) → Queue for triage → Release lock
    OR
    → New message arrives (before debounce fires) → Reset timer → Stay locked
    OR
    → Lock expires (heartbeat timeout) → Release lock (error case)
```

**Implementation (Redis):**

```
Key: conversations:{conversation_id}:lock
Value: {
  "locked_at": "2026-10-10T14:30:00Z",
  "expires_at": "2026-10-10T14:30:30Z",
  "debounce_task_id": "task-xyz",
  "message_count": 3
}
TTL: 30s (prevents deadlock)

Key: conversations:{conversation_id}:debounce
Value: {
  "fires_at": "2026-10-10T14:30:04Z",
  "message_ids": ["msg1", "msg2", "msg3"]
}
TTL: 5s (auto-cleanup after fire)
```

**Lock Acquisition:**

```python
def acquire_conversation_lock(conversation_id: str, ttl: int = 30) -> bool:
    """Acquire conversation lock with TTL."""
    return redis.set(
        f"conversations:{conversation_id}:lock",
        json.dumps({
            "locked_at": datetime.utcnow().isoformat(),
            "expires_at": (datetime.utcnow() + timedelta(seconds=ttl)).isoformat(),
        }),
        nx=True,  # Only set if not exists
        ex=ttl
    )
```

### 3. Debounce Queueing

When a message arrives:

1. Try to acquire lock
   - If lock exists (not acquired): Append to debounce message list, reset timer
   - If lock acquired: Start debounce timer
2. Start background task: `schedule_debounce(conversation_id, wait_seconds)`
3. Task waits `wait_seconds`, then:
   - Check for new messages in debounce list
   - Coalesce all messages into single text block
   - Queue for triage
   - Release lock

**Example: 3 Chat Messages in 5s**

```
T=0s:   "Hi, I have a..."        → Acquire lock, start 4s debounce
T=1s:   "...question about..."   → Reset debounce timer
T=3s:   "...my order"            → Reset debounce timer
T=7s:   Debounce fires           → Coalesce all 3 → Queue triage → Release lock
T=7s:   New message "Thanks!" arrives → Acquire lock, start new 4s debounce
T=11s:  Debounce fires           → Queue triage for 4th message
```

### 4. Coalescing Strategy

**Option A: Concatenation (Simple)**
```
Customer: Hi, I have a...
Customer: ...question about...
Customer: ...my order

Coalesced: "Hi, I have a... question about... my order"
```

**Option B: Thread View (Preserves Context)**
```
Customer (1): Hi, I have a...
Customer (2): ...question about...
Customer (3): ...my order

Coalesced: "[Chat thread with 3 messages] Hi, I have a... | question about... | my order"
```

**Implementation:** Use **Option A** (simple concatenation) for MVP; Option B in v2.

### 5. Lock Release Scenarios

#### 5.1 Normal: Debounce Fires
- Coalesce messages → queue triage → release lock

#### 5.2 New Message During Debounce
- Append to buffer, reset timer (lock stays acquired)

#### 5.3 Lock Heartbeat Timeout (30s)
- Lock expires automatically via Redis TTL
- Log error (indicates slow system)
- Release lock (customer can send again)

#### 5.4 Triage Completes (At-Node-Boundary Cancellation)
- When S2 classification finishes, release lock
- If new message arrived during triage: acquire new lock, start debounce
- This prevents "old triage" results from being stale by the time new messages arrive

### 6. Conversation State Machine

```python
@dataclass
class ConversationState:
    conversation_id: str
    status: Literal["open", "debouncing", "triaging", "escalated", "resolved"]
    last_message_at: datetime
    lock_acquired_at: Optional[datetime]
    debounce_fires_at: Optional[datetime]
    triage_started_at: Optional[datetime]
    
    @property
    def is_locked(self) -> bool:
        if not self.lock_acquired_at:
            return False
        age = datetime.utcnow() - self.lock_acquired_at
        return age < timedelta(seconds=30)  # Hard TTL
```

Add to `conversations` table:

Create outbox event for coalescing:

```sql
CREATE TABLE outbox_coalesce_events (
    id BIGSERIAL PRIMARY KEY,
    conversation_id BIGINT NOT NULL REFERENCES conversations(id),

    coalesced_text TEXT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    processed_at TIMESTAMP,

```

### 8. Error Handling

| Scenario | Handling |
|---|---|
| **Lock acquisition fails (timeout)** | Retry up to 3x with exponential backoff, then skip debounce |
| **Debounce task crashes** | Dead letter to `messages_dlq`, manual retry |
| **Redis down** | Bypass debounce, queue immediately (degrade gracefully) |
| **Conversation doesn't exist** | 404 Not Found |

1. Create `DebounceScheduler` class
   - `schedule_debounce(conversation_id, wait_seconds)` → task_id
   - `get_debounce_status(task_id)` → pending/fired/cancelled
   - `cancel_debounce(task_id)` → idempotent
2. Use background task worker (FastAPI background tasks or Celery)
3. Store task metadata in Redis for observability

### Phase 3: Coalescing & Message Ordering (Day 1.5)
1. Create `MessageCoalescer` class
   - `coalesce(message_ids)` → single text block
   - Preserve order from message timestamps
2. Modify S1.2 ingestion endpoint:
   - After message persisted, acquire lock
   - Start debounce timer
   - Before queueing for triage, check if debounce fired
3. Add `coalesced_message_ids` to triage job payload

### Phase 4: At-Node-Boundary Cancellation (Day 2)
1. Hook into S2 (classification) completion
   - When classification finishes, release lock
   - Check for new messages in buffer
   - If new messages: acquire new lock, start debounce for new batch
2. Idempotency: Release lock only once per batch

### Example: Lock Manager

```python
# packages/api/src/triage/ingestion/locking.py
import json
from datetime import datetime, timedelta
from typing import Optional
import redis.asyncio as redis

class ConversationLockManager:
    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client
        self.lock_ttl = 30
    
    async def acquire_lock(self, conversation_id: str) -> bool:
        """Acquire conversation lock (non-blocking)."""
        key = f"conversations:{conversation_id}:lock"
        now = datetime.utcnow().isoformat()
        expires_at = (datetime.utcnow() + timedelta(seconds=self.lock_ttl)).isoformat()
        
        result = await self.redis.set(
            key,
            json.dumps({
                "locked_at": now,
                "expires_at": expires_at,
            }),
            nx=True,  # Only if not exists
            ex=self.lock_ttl
        )
        return result is not None
    
    async def release_lock(self, conversation_id: str) -> bool:
        """Release conversation lock."""
        key = f"conversations:{conversation_id}:lock"
        await self.redis.delete(key)
        return True
    
    async def is_locked(self, conversation_id: str) -> bool:
        """Check if conversation is locked."""
        key = f"conversations:{conversation_id}:lock"
        return await self.redis.exists(key) > 0
```

### Example: Debounce Scheduler

```python
# packages/api/src/triage/ingestion/debouncing.py
import asyncio
from datetime import datetime, timedelta
import json
import uuid

class DebounceScheduler:
    def __init__(self, redis_client, lock_manager):
        self.redis = redis_client
        self.lock_manager = lock_manager
    
    async def schedule_debounce(
        self,
        conversation_id: str,
        wait_seconds: int,
        message_ids: list
    ) -> str:
        """Schedule debounce and return task ID."""
        task_id = str(uuid.uuid4())
        fires_at = (datetime.utcnow() + timedelta(seconds=wait_seconds)).isoformat()
        
        await self.redis.set(
            f"conversations:{conversation_id}:debounce",
            json.dumps({
                "task_id": task_id,
                "fires_at": fires_at,
                "message_ids": message_ids,
            }),
            ex=wait_seconds + 5  # TTL slightly more than wait time
        )
        
        # Schedule background task
        asyncio.create_task(
            self._debounce_task(conversation_id, task_id, wait_seconds)
        )
        
        return task_id
    
    async def _debounce_task(self, conversation_id: str, task_id: str, wait_seconds: int):
        """Background task: wait and fire debounce."""
        await asyncio.sleep(wait_seconds)
        
        # Debounce fires: coalesce and queue for triage
        debounce_data = await self.redis.get(f"conversations:{conversation_id}:debounce")
        if debounce_data:
            data = json.loads(debounce_data)
            # TODO: Call coalescer and queue for triage
            # Then release lock
            await self.lock_manager.release_lock(conversation_id)
```

## Open Questions

1. Should we coalesce across channel boundaries (e.g., email + chat on same conversation)?
   - **Answer:** No, each channel has separate debounce; assume each inbound channel is separate conversation initially.
2. What if customer sends 100 messages in 4s?
   - **Answer:** Coalesce all into single text block (limit total length to 16KB to prevent LLM token explosion)
3. Should we preserve conversation history in triage payload, or just coalesced messages?
   - **Answer:** Just coalesced messages + last 5 historical messages for context (deferred to S2)
