## Overview

The Sprint 4 acceptance gate validates the end-to-end proactive trigger and escalation pipeline. This includes:
- Anomaly detection (S4.1) triggering escalations
- Proactive outreach (S4.2) campaigns executing correctly
- Manual overrides (S4.3) with feedback loop
- Ops dashboard (S4.4) displaying real-time data
- SLA management (S4.5) tracking and auto-escalation
- Multi-channel routing (S4.6) delivering correctly
- Feedback collection (S4.7) feeding learning
- Context handoff (S4.8) preserving conversation state
- Performance monitoring (S4.9) alerting on degradation

## Acceptance Criteria

### Scenario A: Churn Risk Escalation

**Setup:**
- Customer with health score degradation (75 → 45 over 7 days)
- Anomaly detector identifies trend

**Flow:**
1. S4.1: Anomaly signal triggered (churn_spike)
2. S4.2: Proactive outreach campaign scheduled (email + in-app)
3. S4.4: Dashboard shows "Churn Risk" alert
4. If triage confidence <60%: S4.5 escalates to human queue (P1)
5. S4.6: Slack alert sent to support team
6. S4.8: Context handoff includes health score + trend + prev attempts
7. Human agent accepts/overrides; S4.7 collects feedback
8. S4.9: Metrics recorded (escalation reason, resolution time)

**Assertions:**
- ✓ Anomaly detected within 2s of degradation
- ✓ Outreach campaign created with correct audience
- ✓ Dashboard updated within 5s
- ✓ Escalation queued with correct priority
- ✓ Slack message delivered with full context
- ✓ Handoff completeness score >90%
- ✓ Feedback loop closes within SLA

---

### Scenario B: Fraud Flag & High-Confidence Override

**Setup:**
- Customer flagged for fraud (multiple chargebacks, high-risk country, velocity)
- Triage agent has high confidence (95%) on fraud classification

**Flow:**
1. S4.1: Fraud pattern anomaly detected
2. Agent triage decides: ESCALATE (high confidence, safety override)
3. S4.3: Manual override UI shows override reason options
4. Support team confirms override → adds "customer_confirmed_legitimate" tag
5. S4.7: Override feedback collected
6. S4.9: Metrics show escalation reason + override reason

**Assertions:**
- ✓ Fraud pattern detected within 1s
- ✓ Confidence threshold respected (>90% = trustworthy)
- ✓ Override UI renders with correct reasons
- ✓ Override recorded with timestamp + user + reason
- ✓ Feedback loop updates override reason summary
- ✓ Metrics dashboard shows "override_rate" and "override_reason_distribution"

---

### Scenario C: Low Confidence + Knowledge Gap Escalation

**Setup:**
- Intent classification confidence: 42%
- Entity extraction failed (missing customer_id)
- Knowledge base no matching articles

**Flow:**
1. S2.7 (Triage agent) runs with low confidence
2. S4.3: Escalation triggered (confidence <50% threshold)
3. Escalation reason: "low_confidence + entity_extraction_failure"
4. S4.5: Auto-escalated to P2 queue (standard SLA 4 hours)
5. S4.8: Context includes original message, extracted entities, top 3 KB misses
6. Human resolves, S4.7 captures feedback: "customer_asking_for_feature_X"
7. S3.5 (Knowledge gap analysis) picks up signal → adds to gap list

**Assertions:**
- ✓ Escalation triggered at confidence threshold
- ✓ Queue priority correct (P2)
- ✓ Handoff includes all low-confidence signals
- ✓ KB misses included in context
- ✓ Feedback routed to KG analyzer
- ✓ Next KG report includes this feedback

### Scenario D: SLA Breach Auto-Escalation

**Setup:**
- P1 ticket in queue for 45 minutes (SLA: 30 min)
- No human agent available

**Flow:**
1. S4.5: SLA breach detected at T+45min
2. Auto-escalation triggered: escalate to manager
3. S4.6: PagerDuty alert sent to on-call manager
4. S4.4: Ops dashboard highlights "SLA BREACHED" in red
5. Manager acknowledges within 10 minutes
6. S4.9: Metric recorded (escalation_type: sla_breach, time_to_manager_ack: 8min)

**Assertions:**
- ✓ SLA breach detected within 1 minute of breach
- ✓ Auto-escalation rule executed (manager notified)
- ✓ PagerDuty alert contains ticket summary
- ✓ Dashboard reflects breach prominently
- ✓ Metric recorded with correct classification

### Scenario E: Multi-Channel Escalation with DND

**Setup:**
- Slack escalation target has DND scheduled 4pm–6pm
- Email is secondary channel
- PagerDuty on-call is fallback

**Flow:**
1. S4.6: Escalation routed to Slack (primary)
2. DND check: blocked (4:15pm, within DND window)
3. Fallback: email sent (secondary)
4. Dashboard logs: "Escalation routed to email (Slack blocked by DND)"
5. On-call also notified via PagerDuty for visibility
6. Support team checks email, responds

**Assertions:**
- ✓ DND boundary respected (no Slack message in DND window)
- ✓ Email sent as fallback
- ✓ PagerDuty notified (visibility)
- ✓ Audit trail shows routing decision
- ✓ Metrics include "escalation_routing_reason"

---

### Scenario F: Proactive Campaign & Engagement Tracking

**Setup:**
- Customer engagement score dropped 20% over 2 weeks
- Loyalty program tier: Silver (churn risk moderate)

**Flow:**
1. S4.2: Engagement drop detected
2. Trigger: "loyalty_engagement_campaign" (Silver tier, moderate risk)
3. Campaign created: email + in-app notification
4. A/B variant: "A" (personal offer), "B" (support check-in)
5. Customer assigned to variant "A"
6. S4.9: Campaign metrics tracked (sent, opened, clicked, converted)
7. S4.8: If escalation needed, context includes "in_loyalty_campaign: true"

**Assertions:**
- ✓ Engagement drop detected within daily batch
- ✓ Campaign created with correct tier/risk level
- ✓ A/B assignment consistent
- ✓ Metrics collected (delivery, open, click)
- ✓ Escalation context includes campaign status
- ✓ Campaign ROI tracked (conversion, churn reduction)

## CI Job Configuration

**File:** `.github/workflows/sprint4-acceptance-gate.yml`

```yaml
name: Sprint 4 Acceptance Gate

on: [push, pull_request]

jobs:
  acceptance-tests:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:15
      redis:
        image: redis:7-alpine
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-python@v4
        with: { python-version: "3.11" }
      
      - run: pip install -e .
      - run: pytest tests/eval_harness_s4.py -v
      
      - run: |
          # Anomaly detection latency test
          python tools/benchmark_anomaly_latency.py --target-p99=2000
      
      - run: |
          # SLA accuracy test
          python tools/test_sla_accuracy.py --num-cases=100
      
      - run: |
          # Multi-channel routing test
          python tools/test_routing_latency.py --target-p99=3000
      
      - run: |
          # Context handoff quality test
          python tools/test_handoff_quality.py --min-completeness=0.90
      
      # Gate: all tests must pass
      - name: Report
        if: always()
        run: |
          if [ $? -eq 0 ]; then
            echo "✓ Sprint 4 Acceptance Gate PASSED"
            exit 0
          else
            echo "✗ Sprint 4 Acceptance Gate FAILED"
            exit 1
          fi
```

## Known Risks & Mitigations

| Risk | Mitigation |
|------|-----------|
| Anomaly false positives (alert fatigue) | Threshold tuning in S4.1; ensemble confirmation (EWMA + Isolation Forest) |
| Escalation cascade (low confidence → escalation → another escalation) | Confidence threshold guards (S4.3); max escalation depth = 2 |
| SLA deadline misses under load | Auto-escalation to manager; queue prioritization + assignment algorithm |
| Multi-channel delivery failures (Slack down, email bounce) | Fallback routing (S4.6); audit trail for debugging; retry logic with exponential backoff |
| Context handoff incomplete (missing critical info) | Completeness scorer (S4.8) with quality thresholds; validation tests |
| Override reason misclassification | Manual review + feedback loop (S4.7); retraining triggers on common misses |
